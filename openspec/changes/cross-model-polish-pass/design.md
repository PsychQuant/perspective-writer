## Context

`perspective-writer` 的核心紀律是 Tarski T-schema 與反虛構：每個敘述都要有具體指涉，缺口不得用模糊措辭填補。Phase 1–3 建立書寫者的聲音模型與事實錨點，Phase 4 起草，Phase 5 過作者自審的 anti-pattern checklist。

現況的缺口是：Phase 5 與可選的 Phase 5c 都在同一個模型內完成。同 repo #7 的四輪跨模型盲驗留下對照事實 —— 所有 blocking finding 全部出自跨模型驗證，作者自審每輪都報「完全符合」。

**限制條件**：

- README 的 EXTERNAL-CONSUMER CONTRACT（v2 since 3.0.0）有 live consumer（issue-driven-dev 的 reply-type comment），並以**具名封閉列舉**規定 calibrate mode 下哪些 core section 執行。新增任何 section 都會落在該列舉之外。
- Phase 5c 已確立降級鐵律：偵測失敗即照常完成交付，永不阻斷。任何新階段必須繼承。
- Phase 5c 現有非目標條款寫著「不要求 codex-pro」。
- 外部模型看不到 Phase 1–3 的聲音模型與事實錨點。

**利害關係人**：本 skill 的書寫者（主要）；經 calibrate 契約呼叫的外部 plugin（次要，本設計刻意讓其零影響）。

## Goals / Non-Goals

**Goals:**

- 在交付前加入一道真正外部的潤稿，補上單一模型自審看不見的盲點
- 潤稿在缺依賴、缺授權時逐層降級，最終**必定**交付草稿
- 外部模型不得更動 Phase 1–3 錨定的事實敘述，且此約束**機械可驗**而非仰賴指示
- 迴圈不收斂時對使用者**可見**
- 外部依賴的版本與治理值在執行時解析，樹內不留會老化的複本

**Non-Goals:**

- **不**在 codex-pro 新增潤稿 skill（見 D6 的替代方案評估）
- **不**轉包給 parallel-ai-agents 的 ensemble skills（產出型別為 findings 而非改寫文本；拓撲為 fan-out 而非對話；且會閉合 plugin 間的循環依賴）
- **不**修補 Phase 5c 未列入消費者契約 section 列舉的既有缺口 —— 該缺口為 pre-existing，另案追蹤於 PsychQuant/perspective-writer#11
- **不**修改 consumer-degradation-disclosure 的既有規範（見 D2 連帶結論）
- **不**在本 repo 內 vendor 任何外部執行檔
- **不**處理外部執行檔的所有權歸屬問題 —— 另案追蹤於 PsychQuant/codex-pro#15
- **不**替潤稿迴圈設硬性輪次上限（使用者裁定）

## Decisions

### D1: Phase 5d 置於 Phase 5c 之後、Phase 6 之前

潤稿在草稿呈現給使用者**之前**完成，使用者看到的第一版即為潤稿後版本。

**替代方案**：置於 Phase 6 之後（使用者先確認方向、定稿後才潤）。否決理由 —— 那會讓使用者為同一封信審閱兩次，且第二次審閱的對象是外部模型改過的文本，反而增加而非減少負擔。

**替代方案**：併入 Phase 5c。否決理由 —— 5c 的語意是「多視角**複核**」（產出問題清單），5d 是「**改寫**」（產出文本）。合併會讓 5c 同時承擔兩種產出型別。

### D2: 潤稿不適用於 calibrate mode

Phase 5d 加入消費者契約「does not apply」的具名列舉。

**理由**：契約的 return shape 條款要求回傳內容除狀態標頭與草稿文本外別無他物，潤稿迴圈的任何敘述都會違反；且契約自述 calibrate 過程無人在場，而潤稿的價值前提是有人會看結果。外部 consumer 為自動化流程，會承擔外部往返的延遲與成本卻無人審閱。

**連帶結論**：診斷階段提出的「潤稿管道降級需要第二條 status 軸」**因此不成立** —— 該軸只在 5d 適用於 calibrate mode 時才需要消費者信號。consumer-degradation-disclosure 不需修改。

**性質**：此為 additive 澄清，calibrate 既有行為不變，非 BREAKING。但依 README 自身規定，契約段落變更仍須 bump 並記 CHANGELOG。

### D3: 三層 failure-driven ladder，不設帳號詢問步驟

- 第一層：外部模型（Codex）潤稿
- 第二層：獨立 subagent 潤稿（觸發條件為第一層的授權失效或依賴缺席）
- 第三層：照常交付未潤稿的草稿

**關鍵取捨** —— 原始需求設想「先問使用者有沒有帳號」。改為 failure-driven：直接嘗試，由既有的授權失效類別觸發降級。理由：授權狀態無法從本機狀態可靠推斷（裝了 plugin 不等於有授權，有授權不等於額度未盡），而該失效類別本就是 fail-fast、不重試，探測成本極低。少一個使用者答不出來的提問。

**第二層必須是獨立 subagent**，不得是同一 session 的第二次 pass —— 由起草的同一個模型自己潤，「外部視角」這個本階段存在的理由就消失了。

**降級鐵律**：三層皆須有明確出口通往「照常交付」。任何「因為缺依賴所以不給草稿」的行為都是違規。

### D4: 潤稿約束採 frozen-span 義務與回稿後機械驗證

Phase 1–3 錨定的事實敘述（時間錨點、金額、經手人、流程細節、逐字引用）以 frozen-span 清單隨潤稿請求下達；回稿後逐一驗證每個 span 仍存在且出現次數不變；任一 mismatch 即**回退到潤稿前的自家草稿**。

**理由**：本 repo 已有同構機制 —— 消費者契約的 frozen-anchors 條款要求逐字重現並由呼叫端在回傳後驗證，不符即回退。Phase 5d 只是角色對調：本 skill 從被信任的改寫者變成驗證方。

**替代方案**：只下達風格指示（節奏、贅字、句長）。否決理由 —— 無機械檢查時，通順但飄掉的回稿會靜默通過，正是 consumer-degradation-disclosure 已寫明的失敗式：文本品質不構成「校準確實發生過」的證據。

風格指示仍然給，但屬附加，不是主要約束。

### D5: 收斂條件可觀測但不設硬上限

收斂成立條件：回稿與前一輪的差異僅剩不改變語意的措辭層級，且 frozen-span 驗證通過，且無新增事實主張。每輪印出輪次與差異摘要。

**取捨**：使用者裁定不設硬性輪次上限。本設計不推翻該裁定，而是讓不收斂的情況**可見** —— 成本與延遲不再靜默累積。「無新增事實主張」與消費者契約既有的 no-new-claims 條款同源。

### D6: 依賴解析採引用 canonical 文件，樹內不留複本

治理值（模型、推理強度、逾時）在執行時從外部治理契約解析，樹內**零模型字面**；解析流程**引用**上游既有的 canonical 文件，不在本 repo 貼一份解析邏輯。同時設版本地板與 fail-fast，缺依賴時印一步安裝提示並降至第二層。

**替代方案 A**：在本 repo 內嵌完整解析邏輯（照抄既有 consumer 的形狀）。否決理由 —— 同一段解析邏輯已存在兩處複本，上游文件明文反對內嵌分歧複本。第三份只會多一個分頭老化的地方。

**替代方案 B**：請上游新增一個潤稿 skill，本 repo 完全不碰呼叫細節。否決理由 —— 該 skill 會成為本 skill 與執行檔之間的**第二層薄封裝**，且藏不住任何行為（frozen-span 清單、聲音模型、收斂判斷全在本 skill 這側）；上游既有 skill 皆為「單發並寫結果檔」形狀，多輪迴圈每輪多一次檔案交接。此方案的優點（完全不碰呼叫參數）已另案追蹤於 PsychQuant/codex-pro#15。

**引用式的附帶好處**：上游若日後把執行檔歸位，本 repo 只需改引用目標，不需重寫解析邏輯。

### D7: Phase 5c 非目標條款限定適用範圍而非刪除

Phase 5c 的「不要求 codex-pro」限定為「5c 的 ensemble 複核不得把外部 plugin 升格為前置條件」，並明寫 5d 把它當**可降級的首選**不違反該條。

**該行不得刪除。** 實作者看到表面矛盾時最省事的做法是刪掉它，而那條非目標與「不宣告對 ensemble plugin 的依賴」其實是同一個理由的兩面 —— 避免把可選外部 plugin 變成必要前置、避免形成循環。5d 兩條都不違反。

## Implementation Contract

**Behavior** — 書寫者跑 Compose 或 Revise 完成 Phase 5 後：

- 依賴齊備且授權有效時，看到的草稿為外部模型潤稿並收斂後的版本；過程中每輪可見輪次與差異摘要
- 依賴缺席或授權失效時，看到獨立 subagent 潤稿後的版本，並被告知走了哪一層
- 兩層皆不可用時，看到與現況**逐字相同**的草稿，附一行說明潤稿未執行
- 任何一層的 frozen-span 驗證失敗時，看到的是**潤稿前**的草稿，並被告知回退原因
- 經 calibrate 契約呼叫時，行為與本次變更前**完全相同**

**Interface / data shape**：

- 對外部模型的請求含三部分：待潤草稿、frozen-span 清單（逐字字串，一行一條）、風格指示
- 回稿驗證的判準為「每個 frozen span 仍存在且出現次數不變」
- 治理值於執行時解析，本 repo 樹內不出現任何模型名稱字面
- 消費者契約的具名 section 列舉新增 Phase 5d 一項，歸類於不適用

**Failure modes**：

| 情況 | 行為 | 是否對使用者顯示 |
|---|---|---|
| 依賴缺席 | 降第二層 | 顯示，附一步安裝提示 |
| 授權失效 | 降第二層 | 顯示 |
| 第二層亦不可用 | 降第三層，照常交付 | 顯示一行說明 |
| frozen-span 驗證失敗 | 回退潤稿前草稿 | 顯示，並指出哪個 span 不符 |
| 迴圈未收斂 | 持續，但每輪印輪次與差異摘要 | 顯示 |
| 外部呼叫逾時 | 視同該層不可用，降級 | 顯示 |

**Acceptance criteria**：

1. 移除全部外部依賴後跑一次 Compose，交付的草稿與本次變更前逐字相同，且輸出含潤稿未執行的說明 —— 降級鐵律成立
2. 構造一份含已知 frozen span 的草稿，令潤稿回稿刻意改動其中一個 span，結果為交付潤稿前版本並指出該 span —— 驗證與回退成立
3. 對本 repo 全樹搜尋模型名稱字面，命中數為零 —— D6 的零字面要求成立
4. README 消費者契約的具名 section 列舉中可查到 Phase 5d，且歸類為不適用；CHANGELOG 有對應條目 —— D2 成立
5. Phase 5c 的非目標條款仍在，且帶有適用範圍限定文字 —— D7 成立
6. core skill 的 bootstrap task list 含 Phase 5d 對應項 —— 與既有七個 phase 的追蹤紀律一致

**Scope boundaries**：

- **In scope**：core skill 的 Phase 5d 新增與 Phase 0 / Phase 5c 的連帶修改；README 的契約列舉與 5c/5d 說明段；CHANGELOG；email facet 的**受保護範圍增補**（apply 階段釐清：5d 對兩個 mode 一律執行、沒有觸發決策，所以 facet 增補的是「本文類還有哪些內容要進 frozen span」，不是「何時觸發」）
- **Out of scope**：Phase 5c 自身的契約列舉缺口（#11）；外部執行檔的所有權（codex-pro#15）；consumer-degradation-disclosure 的任何修改；Phase 1–5 既有行為；calibrate mode 的既有行為

## Risks / Trade-offs

- **[潤稿磨掉事實錨點]** 外部模型看不到聲音模型與錨點，可能把具體指涉潤成通順的泛稱，且表面讀不出來 → D4 的 frozen-span 機械驗證與回退；回稿後另跑一次 anti-pattern checklist
- **[不收斂的靜默繞圈]** 無硬上限，而對手是傾向持續提供建議的模型 → D5 的每輪輪次與差異摘要，讓不收斂可見
- **[降級鐵律被侵蝕]** 三層比 5c 的兩態複雜，任一層錯誤處理漏接就會退化成「因為缺依賴所以不給草稿」 → 驗收條件 1 直接量測此性質
- **[Phase 5c 非目標被默默刪除]** 實作者遇到表面矛盾時最省事的做法 → D7 列為明確工作項，驗收條件 5 量測
- **[上游呼叫面無版本保護]** 外部執行檔的參數名稱目前無 semver 契約，改名時可能靜默失效 → D6 的引用式依賴讓改動集中於單點；根因另案追蹤於 codex-pro#15
- **[階段變成承重牆]** 若日後有人讓其他行為依賴潤稿產物，第三層降級就不再安全 → 驗收條件 1 應納入回歸檢查，而非只在本次驗一遍
